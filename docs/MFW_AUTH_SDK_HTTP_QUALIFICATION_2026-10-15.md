# MFW commercial Auth SDK + HTTP qualification

Date: 2026-10-15. PR #30, continuation of the identity-boundary qualification.
Status: isolated integration evidence only; NOT live Auth or production admission.

## What changed

The previous 79 identity regression/signed-fixture cases used a test implementation of the getClaims result interface. This wave uses the **published Supabase Auth SDK itself** (`@supabase/auth-js` 2.117.3), its actual `AuthClient.getClaims` method and real loopback HTTP requests. No source implementation of the SDK is copied, stubbed or replaced.

The new `commercial-http-boundary.js` converts an unambiguous POST route and one raw Bearer header into the existing trusted identity adapter call. Query-scope overrides, tenant/role override headers, request bodies, duplicate authorisation headers, malformed tokens and noncanonical routes are rejected. Public errors expose fixed codes rather than token/provider/member details. Foreign and missing organisation cases produce the same status and response body; this does not establish timing-side-channel equivalence.

This module **registers no live route**. The HTTP server exists only inside the integration test; `server-v2.js` and production startup are unchanged.

## The actual and simulated parts

| Component | Qualification in this wave |
| --- | --- |
| Supabase Auth JavaScript SDK | Actual npm package, exact version and committed SHA-512 lock integrity |
| ES256 / RS256 verification | Actual SDK WebCrypto verification of ephemeral signed fixture tokens |
| JWKS retrieval/cache/new key ID | Actual SDK requests to a local HTTP fixture through its fetch adapter |
| HS256 fallback | Actual SDK calls the Auth user endpoint; a local fixture verifies the symmetric signature |
| HTTP transport | Actual Node HTTP client/server, duplicate headers and body/query/header negatives |
| Session and membership authority | In-memory fixture stores; changes are checked afresh on subsequent requests |
| Token issuer, MFA enrollment, bank/finance sources | Synthetic; not hosted Supabase and not business evidence |
| PostgreSQL/session storage | Not part of this SDK test; separate scratch PG17 qualification remains separate |

The fixture uses the canonical HTTPS issuer `https://mfw-sdk-fixture.invalid/auth/v1` for claims and directs only its approved JWKS/user requests to `127.0.0.1`. Unexpected external destinations and redirects are rejected. Private keys and tokens are generated in process memory and are never saved in repository files or evidence artefacts.

## Tests and acceptance

- **21 HTTP transport cases:** route/scope ambiguity, duplicate bearer, content length, body exclusion, forged tenant/user/role headers, bad bearer and redacted errors.
- **31 SDK-over-HTTP scenarios:** ES256, RS256, symmetric fallback, payload/signature tampering, unknown/new/removed key IDs, JWKS failure, issuer/audience/expiry/not-before, two organisations, session/role withdrawal, metadata spoof, financial AAL2, long token and exact error bodies.

## Remaining release gates

The removed-key test uses a fresh client: **instant invalidation across existing remote JWKS caches is not established**. Session/membership checks remain necessary; cached signature verification is not a current access grant. Real MFA enrollment, hosted token issuance/revocation, current session and membership PostgreSQL stores, application transaction-time rechecks, TLS/reverse-proxy/CORS/rate limits and production HTTP entrypoint remain unqualified.

No actual invoice/payment is created, no production routes are registered and no migration is applied. PR #20 historical-schema/default-privilege admission, independent review and Issue #32 real participant Golden Paths still block production.
